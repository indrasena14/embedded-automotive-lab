From .c to .hex

What happens between saving main.c and the chip running it. Every output on this page comes from a real build of the demo project on this laptop.

The whole pipeline
main.c→ preprocess → main.i→ compile → main.s→ assemble → main.o→ link (+ .ld) → firmware.elf→ objcopy → .bin.hex

One command, arm-none-eabi-gcc, normally runs stages 1–4 in one go. CubeIDE's Build button does the same. The demo's build.sh stops after each stage so you can open every file.

The demo program

main.c
#include <stdint.h>
#define BLINK_MS 500                         // preprocessor

const uint32_t baud_rate = 115200;           // .rodata → flash
uint32_t blink_ms = BLINK_MS;                // .data   → RAM, initial value in flash
uint32_t tick_count;                         // .bss    → RAM, zeroed at startup

static uint32_t add(uint32_t a, uint32_t b)  // .text   → flash
{ return a + b; }

int main(void) {                             // .text   → flash
    uint32_t local = 3;                      // stack
    while (1) {
        tick_count = add(tick_count, local);
        if (tick_count > blink_ms * baud_rate) tick_count = 0;
    }
}

Two more files make it a complete firmware: startup.c (vector table and Reset_Handler) and h735_min.ld (the linker script). CubeIDE generates both for every project.

The five stages

real output
1

Preprocessor

main.c → main.i · gcc -E

Pure text substitution, before any C is understood. #include pastes the header file in, #define names are replaced, and #if blocks are kept or dropped. Comments are removed.

main.c: 25 lines  →  main.i: 94 lines   (stdint.h pasted in)
line 77:  uint32_t blink_ms = 500;      (BLINK_MS is gone)

When a macro misbehaves, look at the .i file to see exactly what the compiler received.

2

Compiler

main.i → main.s · gcc -S

Translates C into assembly for the Cortex-M7, optimizes it, and sorts every item into a section. This is where the -O level matters.

main:
    ldr   r3, .L5          @ address of blink_ms
    ldr   r1, [r3]
    ldr   r3, .L5+4        @ address of tick_count
    ldr   r2, [r3]
    mov   r3, #115200      @ baud_rate folded into the code
    mul   r2, r3, r2       @ blink_ms * baud_rate, once
    ...
.L3:
    adds  r3, r3, #3       @ add(tick_count, local), inlined
    cmp   r2, r3
    bcc   .L2
    b     .L3              @ loop, no store to tick_count
Three things the optimizer did

add() was inlined and has no symbol. local became the constant #3, so it never touches the stack. And tick_count lives only in a register and is never written back to RAM, because nothing else reads it. Hardware registers and variables shared with interrupts need volatile to stop this.

3

Assembler

main.s → main.o · gcc -c

Turns assembly into machine code: a relocatable object file. The sections exist, but nothing has an address yet. References to other files are left as placeholders called relocations.

.text    size 0x28   VMA 0x00000000
.data    size 0x04   VMA 0x00000000
.bss     size 0x04   VMA 0x00000000
.rodata  size 0x04   VMA 0x00000000

00000000 R baud_rate     R = .rodata
00000000 D blink_ms      D = .data
00000000 T main          T = .text
00000000 B tick_count    B = .bss

Each .c file becomes its own .o. A CubeIDE project produces dozens: one for your code, one per HAL driver, one for the startup file.

4

Linker

*.o + .ld → firmware.elf + .map

Combines every .o, follows the linker script to place each section in FLASH or RAM, gives every symbol its final address, and fills in the placeholders. It also writes the .map report.

08000000 R vector_table      first thing in flash
08000012 T Reset_Handler
08000074 T main
0800009c R baud_rate
24000000 D blink_ms          RAM
24000004 B tick_count        RAM
24050000   _estack           top of AXI SRAM

If two files define the same symbol, or a function is called but never defined, this is the stage that fails with multiple definition or undefined reference.

5

objcopy

firmware.elf → .bin / .hex

Strips the .elf down to just the bytes that go into flash. Nothing about the program changes; only the packaging does.

firmware.elf   9,452 bytes   headers, symbols, section table
firmware.bin     164 bytes   exactly what goes into flash
firmware.hex     535 bytes   same 164 bytes as text + addresses

Reading the .bin

first 16 bytes = vector table
offset 0x00:  24050000   08000013   08000011   08000011
              initial SP  Reset      NMI        HardFault
  • 0x2405 0000 is _estack, the top of AXI SRAM. The CPU loads it into the stack pointer at power-on.
  • 0x0800 0013 is Reset_Handler (0x0800 0012) with bit 0 set. Bit 0 marks Thumb code, the only instruction set a Cortex-M runs.
  • A .bin has no addresses. Byte 0 goes wherever you tell the programmer, which must be 0x0800 0000.

.data has two addresses

VMA vs LMA

Every section has a VMA (where it lives while the program runs) and an LMA (where its bytes are stored in the image). For code and constants they're the same. For .data they differ, because RAM is empty at power-on.

From power-on to main()

what the image is for
  1. The programmer (CubeProgrammer or the IDE) writes the image into flash at 0x0800 0000.
  2. At power-on the CPU reads word 0 into the stack pointer (0x2405 0000) and word 1 as the reset address.
  3. Reset_Handler copies .data's values from flash to RAM, so blink_ms becomes 500.
  4. It fills .bss with zeros, so tick_count starts at 0.
  5. It calls main(). CubeIDE's startup file also calls SystemInit() before the copy (FPU access, vector table); the clock tree is set up later, inside main(), by SystemClock_Config().

Startup code, line by line

startup.c

A microcontroller has no operating system. At power-on the CPU knows nothing about C, yet C needs three things ready before main(): a stack, .data holding its starting values, and .bss set to zero. The startup code sets up those three things, then calls main().

A

Symbols from the linker script

extern
extern uint32_t _estack;                  // top of RAM, 0x2405 0000
extern uint32_t _sidata, _sdata, _edata;  // .data: values in flash, start/end in RAM
extern uint32_t _sbss, _ebss;             // .bss: start/end in RAM

These are defined in the linker script, not in C. They aren't real variables. They're addresses the linker calculated, so the code always takes their address with &: &_sdata is 0x2400 0000. Reading _sdata without & would give whatever happens to be stored there.

B

Reset_Handler: the first code that runs

copy, zero, call main
void Reset_Handler(void)
{
    uint32_t *src = &_sidata;          // .data values in FLASH (0x0800 00A0)
    uint32_t *dst = &_sdata;           // .data in RAM (0x2400 0000)

    while (dst < &_edata)              // copy word by word
        *dst++ = *src++;              // read, write, advance both by 4 bytes

    for (dst = &_sbss; dst < &_ebss; ) // zero .bss
        *dst++ = 0;

    main();
    while (1) { }                     // main() has nothing to return to
}

Before the copy loop, blink_ms holds random power-on garbage. After it, 500. The zero loop is what makes C's promise true that globals with no starting value begin at 0.

C

Default_Handler

unexpected interrupts and faults
void Default_Handler(void) { while (1) { } }

A crash or an interrupt with no handler lands here and stays, so with the debugger attached you can pause and see where it stopped (Week 11).

D

The vector table: read by the hardware

.isr_vector
__attribute__((section(".isr_vector"), used))
void (* const vector_table[])(void) = {
    (void (*)(void))&_estack,  // word 0, 0x0800 0000: initial stack pointer
    Reset_Handler,             // word 1, 0x0800 0004: where to start
    Default_Handler,           // word 2: NMI
    Default_Handler,           // word 3: HardFault
};
PartMeaning
void (*)(void)Pointer to a function taking nothing and returning nothing
vector_table[]An array of those pointers
constNever changes, so it lives in flash
section(".isr_vector")Its own section, which the linker script puts first in flash with KEEP()
usedKeep it even though no C code references it; only the hardware reads it
(void (*)(void))&_estackA cast, because every entry must have the same type

At power-on the CPU loads word 0 into the stack pointer and jumps to the address in word 1. Later, each interrupt jumps to its own entry. This demo has 4 entries; CubeIDE's full H735 table has well over 150, one per interrupt source.

E

main.c

the super loop
#include <stdint.h>        // uint32_t is always exactly 32 bits; plain int varies by CPU
#define BLINK_MS 500       // named constant instead of a bare number

static uint32_t add(...)   // static function: private to this file

int main(void) {
    uint32_t local = 3;
    while (1) {            // set up once, then loop forever
        ...
    }
}

while (1), the super loop, is the basic shape of bare-metal firmware. Your first blink project has exactly this structure.

CubeIDE rule

Write your code only between /* USER CODE BEGIN */ and /* USER CODE END */ comments. When CubeMX regenerates the file, it keeps only what's between those markers.

Exercises

1. Add uint32_t boot_count = 1; and find its RAM address and its starting value in the .hex. 2. Comment out the copy loop and predict blink_ms on real hardware. 3. On the board, set a breakpoint on Reset_Handler in CubeIDE and step until main().

  • .bss costs no flash. .data costs flash and RAM. Mark tables const to keep them in flash only.
  • A static local behaves like a global (it keeps its value between calls) but is visible only inside its function.
  • Keep big buffers out of functions, since a stack overflow shows up as a hard fault. Avoid malloc() in firmware: the heap fragments, and most automotive coding standards ban it.

Check yourself

tap to reveal
Which stage turns #define BLINK_MS 500 into 500?

The preprocessor (stage 1). The compiler never sees the name BLINK_MS.

You get "undefined reference to HAL_GPIO_TogglePin". Which stage failed, and what's the usual cause?

The linker. The function is declared in a header, but no .o file in the build defines it, usually because the HAL source file isn't part of the project.

Why is the .elf 9,452 bytes when the .bin is only 164?

The .elf also carries headers, the section table and the symbol table (and debug info when built with -g). Only the 164 bytes of loadable content go into flash.

You flash a .bin at 0x0800 1000 by mistake. What happens at reset?

The CPU reads its stack pointer and reset address from 0x0800 0000, not from your image, so it won't start your program. A .bin carries no address, so the start address you give the programmer must be right. A .hex or .elf carries its own addresses.

Why is blink_ms's initial value in the .hex but tick_count isn't?

blink_ms is in .data, whose value 500 must be stored in flash and copied to RAM at startup. tick_count is in .bss, which is just zeroed at startup, so nothing needs storing.
